# HALOGY CHANGE LOG
--------------------

## Version 2.0.0 (community fork)

- **Runs on modern PHP and databases**: PHP 8.1 or later (tested on 8.3), MariaDB 10.x / MySQL 8; CodeIgniter 2.1 core and HMVC patched for PHP 8; known PHP 8 fatal errors and deprecation warnings fixed across all modules (pages, blog, events, shop, forums, wiki, community, webforms, files, images, users, admin); mysqli driver replaces removed mysql extension; permissive session sql_mode set on connect (dump uses zero dates); DB settings from HALOGY_DB_HOST/USER/PASS/NAME env vars; environment from HALOGY_ENV (defaults to production); ZipArchive replaces removed zip_* functions for image and template zip uploads.

- **Security**: passwords stored with password_hash(); existing MD5 passwords upgraded automatically on next login; remember-me cookie replaced with a signed token (the old one stored the plaintext password and was unserialized from the request); session cookies signed with HMAC-SHA256, random session IDs, regenerated on login, HttpOnly/SameSite; encryption key read from HALOGY_ENCRYPTION_KEY or generated per install (no more shared hard-coded key); fixed privilege escalation where public registration and account forms accepted a posted groupID (an anonymous visitor could make themselves an administrator); CSRF protection for POST requests based on what the browser says about the request: a POST is refused if Sec-Fetch-Site is present and not same-origin, or if Origin is null or foreign, even with a valid token; otherwise it is accepted with a valid token (form field or X-CSRF-Token header), or when Sec-Fetch-Site is same-origin, Origin matches this site, or (when neither header is sent) Referer matches this site; pages are not rewritten, the only addition is a csrf-token meta tag in <head> used by the bundled AJAX code; over HTTPS the cookie uses the __Host- prefix; state-changing actions reached by GET (delete/approve/publish/revert, etc., configured in csrf_protect_get_methods) show a confirmation page with a POST button instead of running; logout runs directly only on same-origin GETs; other HTTP verbs (PUT, DELETE, OPTIONS, etc.) get 405; payment gateway callbacks are exempt; login redirect targets restricted to local paths; member/visitor content is escaped or sanitised everywhere it is shown: wiki pages and categories render Markdown with raw HTML disabled and unsafe link schemes neutralised, bbcode in forum posts/messages/signatures/profiles only allows http(s), mailto and site-relative links, blog comments, shop reviews, support tickets, member names and search terms are escaped in the front end and admin views, and comment websites and referrers link only when they are http(s); admin-authored content allows raw HTML by design; production mode hides PHP and database errors; uploads directory blocks script execution; dangerous file types removed from upload allow-lists; security headers (nosniff, X-Frame-Options, Referrer-Policy); random reset keys and generated passwords; unserialize hardened; SQL injection hardening of admin list ordering; backup no longer leaks other sites' tags.

- **Fixes**: missing "pages_navigation" permission added (navigation admin was inaccessible); backup works with tables lacking siteID; shop upsell rule, order sorting, cart quantity validation; forums/wiki/community fatals; events tag pages; template editor JS error with jQuery 2; webform account creation fatal.

- **Docker**: Dockerfile (PHP 8.3 + Apache) and docker-compose.yml (MariaDB 10.11) for one-command local setup. The image generates its own encryption key at build time (override with HALOGY_ENCRYPTION_KEY; rebuilding without it logs everyone out). docker-compose.yml sets HALOGY_ENV=development, which shows PHP and database errors, so do not expose it publicly.

- **Upgrading an existing install**:
  - back up first
  - run halogy/sql/upgrade-2.0.sql BEFORE deploying the new code or logging in (widens ha_users.password to 255 characters so password hashes are not truncated, and adds the pages_navigation permission; assumes the default ha_ table prefix)
  - check the requirements: PHP 8.1 or later with mysqli, gd, zip and mbstring, and a non-strict MySQL/MariaDB sql_mode (see Requirements)
  - if you run more than one web server, set the same HALOGY_ENCRYPTION_KEY on all of them; changing or losing the key logs everyone out
  - script execution in static/uploads is blocked by an Apache .htaccess; on other web servers (e.g. nginx) configure the equivalent yourself
  - behind a TLS-terminating proxy or load balancer, PHP must see the request as HTTPS: set $_SERVER['HTTPS'] = 'on' in index.php only when your own proxy sets X-Forwarded-Proto (see the CSRF section of halogy/config/config.php), otherwise POSTs from browsers that do not send Sec-Fetch-Site may be refused and the __Host- cookie prefix is not used
  - upload allow-lists were tightened (no js/swf; dangerous types are stripped from web form file types), so review your web form file type settings
  - all users are logged out once, including remember-me logins (cookie formats changed); they can log in with their existing passwords
  - the SQL only adds the permission; tick 'Allow Navigation' for each admin group that needs it
  - configure the database using the new halogy/config/database.php which reads HALOGY_DB_HOST/USER/PASS/NAME (defaults: localhost, halogy, halogy, halogy) and uses the mysqli driver, or edit that file and re-enter your credentials and table prefix (dbprefix is ha_); if you keep your old database.php instead, change dbdriver to mysqli (the old mysql extension was removed in PHP 7)
  - HALOGY_ENV defaults to production, which hides errors; if the upgraded site shows a blank page or HTTP 500, set HALOGY_ENV=development temporarily to see the error; if you let the app create halogy/config/encryption_key.php, make halogy/config read-only again afterwards
  - webform tickets created before 2.0.0 that have uploaded files will show their old HTML link markup as text; new tickets are unaffected
  - See the Upgrading section of README.md for the numbered steps

- **Known limitations**: still CodeIgniter 2.1 underneath (end-of-life framework, patched, not upgraded); some state-changing GET routes are not CSRF-protected (for example, GET admin/pages/add creates a draft page); admin delete/approve/publish links show an extra confirmation page; legacy browsers that send neither Sec-Fetch-Site nor Origin headers rely on the Referer header or a CSRF token; upload script blocking relies on an Apache .htaccess file; changing your password from the front-end account page does not ask for the current password (account forms are per-site templates); forgotten-password pages reveal whether an email is registered, and reset emails include a new plaintext password; reset keys don't expire; backups include only tables with a siteID column (plus tags) — custom tables without siteID are exported as schema only; tickets created before 2.0.0 that stored uploaded-file links as HTML show that markup as text (new tickets list files as plain "name: URL" lines, which the admin view turns into links). This fork as a whole is not recommended for production or internet-facing use.
